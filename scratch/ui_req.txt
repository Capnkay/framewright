1.1 Purpose of this document 
This document defines the problem, scope, data contracts, functional requirements, evaluation rubric, and 
sample artefacts for a student hackathon. Teams will build a system that generates CMS-ready React UI sections 
from one or more of three inputs: a wireframe image, existing source code, and a natural-language prompt. 
1.2 How to use this document 
•  Organisers: treat Sections 1–7 as briefing material and Sections 16–18 as judging guidance. 
•  Students: treat Sections 8–15 as the build contract. The appendices are the expected output shape. 
•  Mentors: use the data model and component contract to review whether generated UI is CMS-editable, 
not only visually similar. 
2. Executive Summary 
Modern websites are no longer static pages. Marketing and product teams need sections that can be edited in a 
CMS after generation: headlines, images, stats, and buttons must have stable element IDs, default fallback 
content, and a Redux (or equivalent) data binding layer. 
The hackathon challenge is to build a generator — not a one-off landing page. Given a wireframe, a code 
snippet, a prompt, or a combination of these, the system must emit: 
1.  A React section component that follows the sample architecture in Appendix C. 
2.  A section metadata record (Appendix A). 
3.  A list of CMS element records (Appendix B). 
4.  A live preview of the generated section. 
Success is measured by layout fidelity, CMS contract compliance, code quality, and the ability to regenerate or 
vary a section without hand-rewriting IDs and bindings. 
3. Problem Statement 
Converting a design into a production-ready, content-managed React section is slow and inconsistent. Typical 
issues: 
•  Wireframes describe layout, but developers invent different class names, spacing, and component 
structure. 
•  Prompts describe intent, but generated JSX is often presentational only — hard-coded text, no IDs, no 
CMS fetch. 
•  Existing section code is difficult to reuse because IDs, Redux selectors, and default content are tightly 
coupled. 
•  Repeatable blocks (stat cards, feature lists) need a loop schema, not three unrelated hard-coded blocks. 
Students must close this gap: an automated pipeline that understands visual structure, textual intent, and code 
patterns, then outputs a section that a CMS editor could later change without touching React source. 
4. Hackathon Objectives 
4.1 Primary objectives (must achieve) 
•  Generate a visually faithful React section from at least two of the three input types (wireframe, code, 
prompt). 
•  Bind every editable field to a unique fieldId and render CMS content with a hard-coded default fallback. 
•  Persist section metadata and element documents in a Node.js API with a document store (MongoDB, or a 
JSON file store if MongoDB is unavailable). 
•  Preview the generated section in the browser using Redux (or equivalent) as the runtime content source. 
4.2 Secondary objectives (strongly recommended) 
•  Accept combined inputs (example: wireframe + prompt that says “make CTA green and use 3 stat cards”). 
•  Support a second variation of the same section (variations field in section metadata). 
•  Re-generate from existing code while preserving element IDs when the layout change is small. 
4.3 Stretch objectives (bonus) 
•  Vision model that labels regions of the wireframe (hero image, badge, H1, stats, CTA). 
•  CSS overlay per fieldId (allSectionsCss) applied after mount. 
•  Export a zip of the generated component plus seed JSON for section and elements. 
•  Simple content editor in the preview that writes back to the element store. 
5. Scope 
5.1 In scope 
•  A student-built generator UI (React) and generator API (Node.js). 
•  One reference page: Home. One reference section: a split hero (image left, content right). 
•  Element types: Image, Text, Textfield, Button, Cards (with loop items), carousel, wizards, etc. 
•  Responsive layout using Tailwind CSS utility classes. 
•  PrimeReact Button (or equivalent accessible button) for the primary CTA. 
•  Placeholder images and fictional brand copy only. 
5.2 Out of scope 
•  Real client brands, real production databases, real storage credentials, and real commit / deploy pipelines. 
•  Full multi-tenant CMS, authentication SSO, payments, or analytics. 
•  Native mobile apps (platform for this topic is Website). 
•  Pixel-perfect Figma plugin work unless a team chooses it as a stretch extra. 
•  Training a foundation model from scratch.

8. Challenge Definition 
Teams build a UI Generation Studio. A user supplies one or more inputs. The studio returns a React section that 
matches the visual structure and is wired for CMS editing. 
8.1 Input mode A — Wireframe 
The user uploads a PNG/JPG/WebP of a section wireframe (low-fidelity boxes or a screenshot-style mock). The 
system infers regions: media, eyebrow/badge, primary heading, subheading, body copy, repeating stats/cards, 
and primary action. 
•  Accept at least PNG and JPG. 
•  Show the uploaded wireframe beside the generated preview for visual comparison. 
•  If a region is uncertain, still emit a plausible element with a default and mark confidence in the API 
response (optional but scored). 
8.2 Input mode B — Existing code 
The user pastes a React section (or a simplified JSX tree). The system must parse structure, extract 
text/image/button nodes, assign or reuse fieldIds, and emit a CMS-compliant component plus element JSON. 
This mode tests understanding of the contract, not only image-to-layout. 
•  Detect hard-coded strings and lift them into element records with defaults. 
•  Detect repeating children and convert them into a Cards loop. 
•  Preserve Tailwind layout classes when they already express the wireframe. 
8.3 Input mode C — Prompt 
The user types intent, for example: “Create a fitness hero. Left image of an athlete. Right side: red uppercase 
badge, bold headline, supporting paragraph, three stats, full-width red CTA.” The system must produce the same 
contract as modes A and B. 
•  Prompt-only generation is valid, but layout should still be responsive (stacked on mobile, split on 
desktop). 
•  The prompt may override colours, copy, number of cards, and CTA label. 
8.4 Combined inputs (recommended) 
Priority when inputs conflict: 
1.  Prompt instructions win for copy, colour, and CTA behaviour. 
2.  Wireframe wins for spatial layout (columns, order, alignment). 
3.  Existing code wins for technical patterns (Redux selectors, helper names, class conventions) unless the 
prompt asks to change them. 
9. Reference User Journey 
1.  Open the Generator Studio at /generate. 
2.  Choose input: Wireframe, Code, Prompt, or Combine. 
3.  Optionally set pageName (default Home) and sectionName (default Custom). 
4.  Submit. The Node API runs analysis + generation. 
5.  API writes a section document and N element documents, then returns generated JSX (or a component 
file path) plus IDs. 
6.  Frontend loads /preview/Home, dispatches fetchElementsByIds, and renders the section. 
7.  User may edit an element in a side panel; preview updates from store data, not from re-generating JSX.

12. Generated Component Contract 
Every generated section MUST follow these rules. Judges will open the file and the DOM. 
12.1 Mandatory rules 
R1.  Declare a const ids object mapping semantic names to fieldId strings. 
R2.  Accept pageName as a prop with a sensible default (Home). 
R3.  On mount, dispatch fetchElementsByIds with every fieldId used in the tree, including nested card field 
IDs. 
R4.  Read live values from state.cms.allSections[pageName]. 
R5.  Every editable node has id={ids.something} or id={item.fieldIdN}. 
R6.  Text nodes use dangerouslySetInnerHTML with a default fallback: data?.[id] || "DEFAULT". 
R7.  Images use a getImage helper, VITE_STORAGE_URL prefix, blob: passthrough, and onError placeholder. 
R8.  Buttons use PrimeReact Button (or documented fallback) with label from CMS and an onClick stub. 
R9.  Repeating items render from a loop array with a DEFAULT_* constant when CMS data is missing or the 
wrong length. 
R10.  Apply allSectionsCss to matching DOM ids after cssData changes. 
R11.  Use Tailwind for layout. Desktop: two columns. Mobile: stacked. Include a max-width container. 
R12.  Add class dynamicStyle on text/button nodes and dynamicStyle2 on images so a future editor can hook 
them. 
R13.  Do not embed real secrets, real bucket URLs, or real customer identifiers. 
R14.  Export default the section component. 
12.2 Accessibility and quality rules 
•  Images have meaningful alt text derived from the prompt or a generic description. 
•  CTA has aria-label. 
•  Colour contrast: body text gray-500+ on white is acceptable; do not put gray-400 on white for long copy. 
•  Do not leave empty id attributes on nested card fields (the sample in Appendix C includes ids on both stat 
value and label). 
12.3 What generated code must NOT do 
•  Hard-code production storage hosts. 
•  Import internal proprietary helpers that students cannot implement (replace with local utils). 
•  Skip Redux and only render defaults. 
•  Use Math.random() for field IDs on every render (IDs must be stable and persisted).

19.1 Disqualification / major penalties 
•  Submitting real client data, secrets, or production URLs: 0 for security and possible disqualification. 
•  Frontend not in React.js or backend not in Node.js: topic requirement failed (cap at 20 unless exception 
granted).

20. Rules and Constraints 
•  Teams of 2–4 unless the organiser states otherwise. 
•  Open-source libraries are allowed. Document them in README. 
•  LLM APIs are allowed. Teams must run with a missing key in a degraded way (clear error), not a crash. 
•  Internet may be limited; a prompt-template fallback that still emits the contract is valued. 
•  All demo content must be fictional (Pulse Fit / sample-brand). 
•  Mentors may clarify requirements but will not write the generator for a team.

function getImage(image) { 
  if (!image) { 
    return `${import.meta.env.VITE_STORAGE_URL}default/images/hero-placeholder.jpg`; 
  } 
  if (image.includes("blob:")) { 
    return image; 
  } 
  return `${import.meta.env.VITE_STORAGE_URL}${image}`; 
} 
  
function errorImage(event) { 
  event.target.src = `${import.meta.env.VITE_STORAGE_URL}default/images/hero-placeholder.jpg`; 
}

Appendix F — Data sanitisation policy used in this brief 
The following were removed or replaced relative to any internal examples used to design the topic: 
•  Real project / brand names → sample-brand / Pulse Fit. 
•  Real MongoDB ObjectIds → placeholder 24-character ids. 
•  Real 10-digit production field IDs → 1000… / 2000… / 3000… ranges. 
•  Real storage and CDN URLs → VITE_STORAGE_URL only. 
•  Git commit hashes, deploy flags, and internal request filenames → omitted or replaced with 
sample/wireframes/hero-section.png. 
•  Internal package paths and proprietary helper names → short local equivalents (fetchElementsByIds). 
•  Employee or machine file paths → not included. 
Students and organisers must apply the same policy to anything they add during the event.
