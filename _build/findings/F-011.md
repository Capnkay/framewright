## What is wrong

`extractAccent` falls back to "any recognised colour word anywhere in the prompt", so a colour
describing the **background** becomes the **accent**.

Measured:

| prompt | resulting `theme.accent` | warned? |
|---|---|---|
| `the background is white` | `gray-50` | yes |
| `a hero on a white surface` | `gray-50` | yes |
| `dark grey background, three stats` | `gray-500` | yes |
| `white card backgrounds` | `gray-50` | yes |

`gray-50` as an accent is a near-white CTA on a white surface — effectively invisible, and it
also undercuts §7's accessibility note ("body copy is `gray-500` or darker on white").

**It is recorded, not silent.** Every case above appends the §6.1-rule-5 warning added at
T-093 ("Prompt set the accent to …; theme.accent and designTokens.colors.accent both moved"),
so the Glass Box shows the decision and a reader can see what happened. That is the difference
between this being MINOR and being MAJOR.

## Two smaller asymmetries in the same extractor

- **`stats: four` misses.** `four stats` → 4, but `stats: four` → 3 with `found: false`. The
  noun-first branch matches digits only (`\b(?:CARD_NOUNS)\b\s*[:=-]?\s*(\d{1,2})`), while the
  word-number branch is value-first only.
- **`TWELVE stats` → 3, not 10.** `NUMBER_WORDS` stops at ten, so a word-number above ten
  falls all the way back to the default rather than clamping to `MAX_CARD_COUNT`.

Both warn, and both are arguably correct-by-accident: `40+ stats` also declines to read `40` as
a card count, which is the right answer, because `40+` is a stat *value* in the reference set
(`1000+`, `40+`, `150+`) rather than a count.

## Where

`server/src/generate/promptToIrKeyless.js` — `extractAccent()`'s `anyColour` fallback, and
`extractCardCount()`'s `nounFirst` / `wordsFirst` patterns.

## Why it matters

Low stakes, and worth being honest about that. §6.1 rule 5 makes the prompt authoritative for
colour, so a prompt mentioning a colour *should* move the accent — the extractor is doing what
it was told, just over too wide a window. The consequence is a washed-out CTA in one demo
prompt shape, visible in the warnings, fixable by rephrasing.

It is filed rather than fixed because the fix has a real risk of being worse: narrowing the
fallback to "only a colour adjacent to an accent noun" would make `make it green` — a
perfectly ordinary instruction — stop working. Getting that trade right needs the prompts the
demo script actually uses, which are in `docs/ROADMAP.md`'s demo section and were not written
with this in mind.

## How to reproduce

```
node -e "
(async()=>{
const K=await import('./server/src/generate/promptToIrKeyless.js');
for(const p of ['the background is white','dark grey background, three stats','stats: four','TWELVE stats']){
  const ir=K.promptToIrKeyless(p);
  console.log(JSON.stringify(p).padEnd(38), ir.theme.accent, '| cards='+ir.cards.count);
}
})();
"
```

## Suggested fix

Not a code change first — **decide the policy against the real demo prompts.** Then, if the
narrowing is wanted:

1. Keep the near-accent branch as the primary (it already handles `green accent`,
   `accent: blue`, `brand colour teal`).
2. Add an explicit **surface** branch that consumes a colour adjacent to
   `background|surface|section|card` and routes it to `theme.surface` /
   `designTokens.colors.surface` instead of the accent — which is where the prompt meant it to
   go, and is a feature rather than a suppression.
3. Only then narrow the bare-colour fallback, so `make it green` still lands on the accent.
4. Extend `nounFirst` to accept number words, and let a word-number above ten clamp to
   `MAX_CARD_COUNT` with the existing `clampedFrom` warning rather than falling back to 3.
