## What is wrong

`artifactRef(jobId, ...)` interpolates `jobId` straight into a filesystem path with no
validation, and the default artifact writer creates whatever directory that yields.

Measured:

```
artifactRef('job-0000000001', 3, 'out')  -> artifacts/job-0000000001/s3-out.json
artifactRef('../../etc/passwd', 3, 'out') -> artifacts/../../etc/passwd/s3-out.json
artifactRef('job-1/../../..', 3, 'out')   -> artifacts/job-1/../../../s3-out.json
```

`defaultWriteArtifact` then runs `fs.mkdir(path.dirname(ref), { recursive: true })` followed
by `fs.writeFile(ref, ...)` — so a traversing `jobId` writes outside `artifacts/`.

## NOT currently reachable — this is defence in depth, not a live hole

Every call site was checked and every one passes a store-generated id:

- `server/src/routes/generate.js` — `trace.runStage(job.jobId, …)`, `trace.skipStage(job.jobId, …)`
- `server/src/routes/regenerate.js` — same
- `jobStore.validateJob` enforces `^job-[0-9]{10}$` on the id it mints (`formatJobId`)
- the URL-facing routes validate before use: `server/src/routes/artifacts.js` and
  `server/src/routes/index.js` both gate on `/^job-\d{10}$/`

So today the traversing value cannot arrive. This finding is filed because the *guarantee*
lives entirely in the callers, and `runStage` is a public function on a shared module.

## Where

`server/src/jobs/stageTrace.js` — `artifactRef()` and `defaultWriteArtifact()`.

## Why it matters

§11.2 fixes the artifact location: "Artifacts are owned by Node and live on the Node machine,
under `artifacts/<jobId>/<stage>-<name>.<ext>`". A path that escapes that root violates the
one structural promise the section makes, and `artifacts/` is gitignored precisely so its
contents are never committed — a file written *outside* it has no such protection.

The reason to fix it now rather than later: **T-064 (replay-from-stage into the Timeline UI) is
unbuilt and will call into the stage trace from a URL parameter.** The next person to wire a
`:jobId` param through to `runStage` inherits a write-outside-root primitive and has no reason
to suspect it, because nothing in `stageTrace.js` says the caller owns validation.

## How to reproduce

```
node -e "
(async()=>{
const {artifactRef}=await import('./server/src/jobs/stageTrace.js');
console.log(artifactRef('../../etc/passwd',3,'out'));
})();
"
```

## Suggested fix

Validate in `artifactRef` and refuse rather than sanitise — `jobId` has exactly one legal
shape and it is already written down in two other files:

```js
const JOB_ID = /^job-[0-9]{10}$/;   // §11.1's own shape, as jobStore.validateJob enforces
if (!JOB_ID.test(String(jobId))) {
  throw new Error(`artifactRef: jobId must match ^job-[0-9]{10}$ (§11.1), got ${JSON.stringify(jobId)}`);
}
```

Refusing beats rewriting: a silently rewritten path writes the artifact somewhere the stage
record does not point at, which is the trace-lies failure mode already recorded in the
corrections register for the retry/artifact-collision gap.

Worth also noting the shape is now defined in four places (`jobStore.validateJob`,
`routes/artifacts.js`, `routes/index.js`, and this fix). One exported constant would be
better, but that spans three tasks' files and belongs to whoever owns the job module rather
than to this fix.
