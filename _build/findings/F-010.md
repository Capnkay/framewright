## What is wrong

§18.2 says: "Emit. **Parse the result with `@babel/parser`** and lint it." T-094 does exactly
that — but `@babel/parser` is **not installed**, so the documented weak fallback is the code
path actually running, and it passes real syntax errors.

Measured against `createValidateAndRecover().check()`:

| source | verdict |
|---|---|
| `export default function H(){return <section` | rejected — unclosed delimiter |
| `export default function H(){return null;` | rejected — unclosed delimiter |
| `export default function H(){ const = 5; return null; }` | **ACCEPTED** |
| `export default function H(){ } }{` | rejected — unbalanced |

`const = 5;` is a hard `SyntaxError`. `@babel/parser` would throw on it. The fallback — a
delimiter-balance scan plus a default-export check — cannot see it.

```
node -e "import('@babel/parser').then(()=>console.log('YES')).catch(()=>console.log('NO'))"
-> NO
```

## Where

`server/src/generate/validateAndRecover.js` — `defaultParse()` catches
`ERR_MODULE_NOT_FOUND` and falls through to `shallowStructuralCheck()`.

The package **is** declared: `server/package.json` lists `"@babel/parser": "^8.0.4"` in
`dependencies`. Nobody has run `npm install` at the repository root, and bare specifiers
resolve upward from the importing file — never sideways into `server/node_modules` — which is
the same trap F-005 recorded for `mongodb`.

## Why it matters

§18.2 exists because "a component that does not parse is not a low-scoring component. It is
not a component. Shipping it with a warning attached would satisfy §18 as written and hand a
judge a broken preview, which is the outcome the whole document exists to prevent."

With the fallback active, a model-authored component containing an ordinary syntax error
passes the structural gate, is never retried, never triggers the deterministic fallback, and
is written to `client/src/sections/generated/`. The preview then fails to compile — in front
of a judge — which is the exact outcome §18.2 was written to make impossible.

The module documents this limitation honestly ("It will not catch a subtle syntax error…
acceptable only because step 3's fallback is the deterministic emitter"). That reasoning was
sound but rested on an assumption that turned out false: it assumed `@babel/parser` would be
present and the fallback would be a cold path. It is the only path.

**Three other suites fail the same way**, so this is one gap, not four:

```
tests/code-to-ir.test.mjs      Cannot find package '@babel/parser'
tests/element-schema.test.mjs  Cannot find package 'ajv'
tests/stage1.test.mjs          Cannot find package 'multer'
tests/route-binding.test.mjs   Cannot find package 'express'
```

Full suite: **535 passing, 4 failing** — every failure a missing package, none a code defect.
This also means **the pre-submit gate cannot currently run clean**, which T-076 requires.

## How to reproduce

```
npm test                       # 4 failures, all ERR_MODULE_NOT_FOUND
node -e "
(async()=>{
const {createValidateAndRecover}=await import('./server/src/generate/validateAndRecover.js');
const {check}=createValidateAndRecover();
console.log(await check('export default function H(){ const = 5; return null; }'));
})();
"                              # -> { ok: true }  <-- should be false
```

## Suggested fix

1. **Run `npm install` at the repository root.** That is the whole fix for the active-path
   problem, and it also clears the four failing suites. The dependencies are already declared
   and their licences already cleared in the README table.

2. **Then make the fallback loud rather than silent.** Once the real parser is the normal
   path, `defaultParse` falling back should append a warning naming why — a structural gate
   quietly running in reduced-strength mode is worse than one that says so, and §11.1 already
   has the vocabulary for it (`degraded`).

3. Consider whether `@babel/parser` belongs in the **root** `package.json` as well.
   `server/src/generate/codeToIr.js` and this module both import it as a bare specifier while
   the tests that exercise them run from `tests/`, so root is where resolution actually looks.
   That is the packaging half of F-005's lesson, and it is unresolved for four packages now.

## Found by

Self-audit of the generation track. The defect is not in T-094's logic — its 21 tests pass and
its retry/fallback behaviour is correct — it is that the environment silently downgraded which
parser T-094 uses. Producer-verifying-producer; see the note on F-008.

## Fixed — 2026-08-21, by installing the declared dependencies

`cd server && npm install` (172 packages, 0 vulnerabilities) and `cd client && npm install`
(151 packages). This was forced rather than chosen: `.githooks/pre-push` now requires **both**
`server/node_modules` and `client/node_modules` before it will run the §9 store-liveness
check, so no push was possible without it.

**Verified — `@babel/parser` is now the active parser and catches what the fallback missed:**

```
check('export default function H(){ const = 5; return null; }')
  before -> { ok: true }                      <-- the defect
  after  -> { ok: false, error: 'Unexpected token (1:35)' }
```

"Unexpected token (1:35)" is a real Babel diagnostic, not the fallback's delimiter message,
so step 1 of §18.2's policy is genuinely being executed.

**Full suite: 551 passing, 0 failing** (was 535 / 4). All four `ERR_MODULE_NOT_FOUND` suites
— `code-to-ir`, `element-schema`, `stage1`, `route-binding` — pass.

### Correction to suggestion 3 above

Suggestion 3 proposed adding `@babel/parser` to the **root** `package.json`. **That is not
needed, and the reasoning behind it was half wrong.** Measured:

```
import('@babel/parser') from the repo root      -> fails
check() inside server/src/generate/…            -> succeeds, using Babel
```

Bare specifiers resolve *upward from the importing file*, so
`server/src/generate/validateAndRecover.js` finds `server/node_modules/@babel/parser`
correctly. A root-level import cannot, but nothing imports it from the root. The upward-only
rule that made F-005's `mongodb` case a trap is the same rule that makes this case fine — the
difference is which directory the importing file sits in, and this one sits under `server/`.

### Noted, outside this finding's scope
