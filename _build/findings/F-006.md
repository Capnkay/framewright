## What is wrong

`server/src/schemas/job.schema.json` documents a floor ruling that has since been **reversed
upstream**, and names the two unclaimed tasks that will read it as authoritative.

The file omits the conventional `$schema` declaration and substitutes a non-standard
`"schemaDraft": "draft-07"` key, with a note explaining why:

> NOTE ON THE MISSING $schema KEY: [...] the conventional `$schema` declaration is
> deliberately absent, because its value is an absolute URL on the json-schema spec host and
> the §14 pre-push gate scans full git history for non-local hostnames.
> `docs/corrections/REGISTER.md` records the identical case [...] and the ruling was to drop
> the field rather than widen the gate's allow-list. [...] **T-019, T-020 and T-021 add three
> more schema files and will each hit this.**

That was true when written. It is not true now. `ALLOWED_HOST_RE` in `.githooks/pre-push`
includes `json-schema.org`, and T-019 landed `server/src/schemas/ir.schema.json` using the
declaration normally:

```json
"$schema": "http://json-schema.org/draft-07/schema#"
```

So the gate was widened after all — the opposite of the ruling the note records — and the
repository now holds two schema files following contradictory conventions, with the
contradicted one asserting its convention confidently and citing the register for it.

## Where

- `server/src/schemas/job.schema.json:4` — `"schemaDraft": "draft-07"`
- `server/src/schemas/job.schema.json:5` — the `description` containing the stale note
- `server/src/schemas/ir.schema.json:2` — `$schema` used normally, gate green
- `.githooks/pre-push:131` — `ALLOWED_HOST_RE`, which now lists `json-schema.org`

## Why it matters

Low severity because nothing is broken: Ajv's default export validates draft-07 without the
declaration, so `job.schema.json` works exactly as intended and every suite is green.

It matters because of **who reads it next**. The note explicitly instructs the claimants of
T-020 (`section.schema.json`) and T-021 (`element.schema.json`) to expect the gate to reject
`$schema` and to omit it. Acting on that produces two more files carrying a workaround for a
problem that no longer exists, and the workaround is the kind that survives — a
non-standard `schemaDraft` key looks deliberate, is documented at length, and cites the
register, so the next person to notice has to re-derive the whole question before touching
it. That is how a temporary carve-out becomes permanent.

The note's own reasoning is also worth preserving as correct-at-the-time. Dropping the field
rather than widening the allow-list was the conservative call, and the register records the
`.claude/settings.json` precedent for it. Someone later decided the spec host was safe to
allow. Both decisions are defensible; only their coexistence is not.

## How to reproduce

```
grep -n 'json-schema.org' .githooks/pre-push
grep -n '\$schema' server/src/schemas/ir.schema.json
grep -n 'schemaDraft' server/src/schemas/job.schema.json
sh .githooks/pre-push origin <remote-url>    # exit 0 — ir.schema.json's URL passes
```

Verified: the gate exits 0 on current history with `ir.schema.json`'s `$schema` URL in it.

## Suggested fix

For whoever claims T-020 or T-021 — **use `$schema` normally**, matching `ir.schema.json`.
The host is allow-listed and the gate is green on it.

Separately, and as a one-line job for whoever next has a legitimate reason to touch
`job.schema.json`: replace `schemaDraft` with a real `$schema` and delete the note. Worth
doing, not worth a dedicated claim, and **not** worth a drive-by edit from an unrelated task —
`AGENTS.md` is explicit that a tidy-up outside a task's declared `files` creates a merge
conflict for someone asleep, and this one is cosmetic.

Flagged rather than fixed for that reason: `job.schema.json` is T-022's committed file and
this finding was raised from a T-009 claim.
