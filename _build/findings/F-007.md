## What is wrong

`docs/model_architecture.jpg` and `docs/model_detailed_architecture.jpg` both present
**Florence-2 as a working pipeline stage** — "Florence-2 Layout Analysis" and "Visual Feature
Extractor (using Florence-2)".

We measured Florence-2 on a real wireframe on our own hardware and it scored **0 of 7,
twice** — once with the wrong task token and once with the right one.
`docs/BENCHMARK-RESULTS.md` B-001 is marked DEFINITIVE and VERIFIED. Asked to detect objects
unprompted it returned one box labelled `"whiteboard"`.

Both diagrams therefore advertise, to a judge, a capability our own measurement disproved.

## The second half, which is worse because nobody has checked it

Both diagrams route detection through **DETR**. DETR's licence is fine — Apache-2.0, approved
in the README table — so this is not a licence problem. It is the *same training-distribution
problem* EC-008 documents:

> general vision models are trained on photographs. Nothing in that distribution teaches that
> a line drawing decomposes into UI components. This is not fixable by prompting.

DETR is COCO-trained. COCO is person, car, chair — photographs. That is precisely why YOLOv8
was rejected on **capability** grounds as well as licence grounds
(`docs/html/stages/01-vision-understanding.html`: *"Pretrained on COCO — person, car, chair.
No UI classes at all"*).

**DETR has never been benchmarked here.** It appears in two diagrams as the primary object
detector, and the one measurement we have on a comparable model says it will return
approximately nothing. That is an unverified assumption on the critical path of the
input-coverage criterion.

## Why it matters

`docs/ROADMAP.md` converts the Florence-2 failure into our strongest demo asset: *"generic
models do not read wireframes, here is the evidence, so we built something that does."* A
diagram showing those same generic models as the working pipeline throws that away and
replaces it with a claim a judge could falsify by asking one question.

## How to reproduce

Open either image. Compare against `docs/BENCHMARK-RESULTS.md` B-001 and `docs/EDGE-CASES.md`
EC-008.

## Suggested fix

1. **Benchmark DETR on the same wireframe, the same way Florence-2 was benchmarked.** About

   Either it works — in which case this finding is wrong and we have a second measured

2. **Redraw both diagrams to lead with contour detection + PaddleOCR**, as
   `docs/html/architecture.html` already does, keeping DETR and Florence-2 visible as
   *measured and rejected* rather than as working stages.

## Measured — 2026-08-20, T-097

**The DETR half of this finding is confirmed, and it is now a number rather than an
inference.** `docs/BENCHMARK-RESULTS.md` B-002.

DETR on the same wireframe B-001 used, fed through stage 2's normaliser first so the input
could not be blamed:

- **One detection**, labelled `"cell phone"`, covering **64% of the frame**
- **Identical at thresholds 0.5, 0.3, 0.1 and 0.05** — the model does not have seven weak
  hypotheses under a cutoff, it has one
- **0 of 7 targets located**
- `ui_labels_available: []` — **DETR's COCO vocabulary contains no UI classes at all.** It
  cannot emit `button`, `heading`, `card` or `badge`; those labels do not exist in its
  output space. No threshold or prompt reaches them.

Read against B-001: Florence-2 returned one box labelled `"whiteboard"` at 84% coverage.
**Two independent architectures, two training sets, the same failure twice.** Both describe
the picture correctly and answer a different question from the one asked.

EC-008 predicted exactly this for DETR, on the grounds that COCO is photographs. The
prediction held.

### What remains open

The measurement is done; the **diagrams are not fixed**. `docs/model_architecture.jpg` and
`docs/model_detailed_architecture.jpg` still show DETR as the primary object detector and
Florence-2 as a working layout analyser. Both are now contradicted by two of our own
benchmarks.

Redraw them the way `docs/html/architecture.html` is drawn: lead with contour detection and
PaddleOCR, keep DETR and Florence-2 visible as **measured and rejected**, each with its
number. The rejection is the asset — it is what converts the architecture from an assertion
into a measurement, and a judge can check it.
