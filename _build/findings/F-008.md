## What is wrong

`applyIdPolicy` issues **the same `fieldId` to two different elements** when an IR carries
two elements with the same `elementName`.

Measured:

```
ir.elements = [
  { elementName: 'headlineMain', default: 'A', sourceOf: 'default' },
  { elementName: 'headlineMain', default: 'B', sourceOf: 'default' },
]
existing    = [{ elementName: 'headlineMain', fieldId: '2000000003', content: 'STORED' }]

-> elements: [ headlineMain=2000000003:STORED, headlineMain=2000000003:STORED ]
-> DUPLICATE fieldId issued? true
```

Both elements resolve through the same `byName` lookup, both find `2000000003`, and neither
allocation path fires — so the duplicate is issued silently, with no warning.

## Where

`server/src/generate/applyIdPolicy.js` — the `byName.get(elementName)` / `preserveMap[elementName]`
resolution inside the `for (const irEl of irElements)` loop.

Root cause is upstream of that, though: **the IR schema does not require `elementName` to be
unique.** `server/src/schemas/ir.schema.json` constrains `elements` as an array of objects
with no uniqueness constraint across them.

## Why it matters

§1 rule 2: "Allocated centrally. A single counter per range, persisted. **Two concurrent jobs
must never receive the same ID.**" A duplicate issued to two elements in the *same* job is a
stronger violation of the same invariant.

§14's pre-submit gate exists specifically to catch duplicate IDs, and T-071 wired it into
`.githooks/pre-push` — the corrections register for CONTRACT v1.1→v1.2 records why:

> "A read-modify-write counter issues duplicates that are perfectly in range. The gate was
> blind to the failure the atomicity rule exists to prevent."

So this defect manufactures precisely the condition the gate is built to reject. It would be
caught at push time, not at generation time — which means it surfaces as a blocked push for
whoever runs the demo, not as an error where the bug is.

**It is reachable from untrusted input.** §16.2 says "Model output is untrusted input." The
hosted prompt-to-IR path (T-027) validates a model's IR against the schema — which permits
duplicate `elementName` — so a model that emits two `headlineMain` elements passes validation
and reaches `applyIdPolicy`. Two DOM nodes then share one `id`, which also breaks R5 and the
§9 store-liveness assertion's "every field ID in `ids` is present in the DOM" check, since
`ids` is a JS object literal and the second key silently overwrites the first.

## How to reproduce

```
node -e "
(async()=>{
const {applyIdPolicy}=await import('./server/src/generate/applyIdPolicy.js');
let n=2000000010; const allocateId=async()=>String(n++);
const ir={elements:[
 {elementName:'headlineMain',contentType:'Text',default:'A',sourceOf:'default'},
 {elementName:'headlineMain',contentType:'Text',default:'B',sourceOf:'default'}],
 cards:{items:[]},idPolicy:{mode:'preserve',contentPolicy:'keep',preserve:{}}};
const existing=[{elementName:'headlineMain',fieldId:'2000000003',contentType:'Text',content:'STORED',loop:null}];
const r=await applyIdPolicy({ir,existingElements:existing,allocateId,isRegeneration:true});
console.log('duplicate?', r.elements[0].fieldId===r.elements[1].fieldId);
})();
"
```

## Suggested fix

Two layers, because the boundary check is the one that makes the failure recoverable:

1. **Reject duplicate `elementName` in the IR validator** (`server/src/validate/irValidator.js`).
   This is the right layer: §6's `idPolicy.preserve.elements` is a `{ elementName: fieldId }`
   map, so duplicates are already structurally unrepresentable in the contract — the schema
   simply never said so. Rejecting there means T-027's hosted path treats it as a
   schema-invalid response and **falls back to the keyless path**, per §16.2, instead of
   propagating a crash. Untrusted input is refused at the boundary, which is where §16.2 says
   it should be.

2. **Guard in `applyIdPolicy` as defence in depth** — a second element claiming an already
   issued `fieldId` should be a loud error, not a silent reuse. `applyIdPolicy` is called by
   the generate, regenerate and replay routes; it should not be able to hand any of them a
   duplicate regardless of what validated upstream.

Do **not** fix this by de-duplicating silently (keeping the first, dropping the second). An IR
with two elements of the same name is malformed, and quietly discarding half of it produces a
component missing a node the IR asked for — the same class of invisible failure §9 exists to
prevent.

## Fixed — 2026-08-21, both layers as suggested

**1. Boundary.** `validateIr` now rejects a duplicate `elementName`
(`checkElementNamesAreUnique` in `server/src/validate/irValidator.js`). Expressed in code
rather than in `ir.schema.json` because draft-07 has no cross-item uniqueness keyword for a
property of array items. This is the layer that matters for untrusted input: §16.2 has the
hosted model's response validated against this schema, so a model emitting two `headlineMain`
elements is now a schema-invalid response and **falls back to the deterministic keyless path**
rather than reaching the allocator.

**2. Defence in depth.** `applyIdPolicy` throws on a duplicate `elementName`. The generate,
regenerate and replay routes all call it directly, without necessarily passing through
`validateIr` first, so it must not be *able* to issue a duplicate whatever validated upstream.

Not fixed by silently de-duplicating, per the note above: dropping the second element would
produce a component missing a node the IR asked for.

### Verified

The original probe, re-run:

```
boundary  : validateIr rejects? true
downstream: refused -> applyIdPolicy: duplicate elementName "headlineMain" in ir.elements...
```

Seven regression tests added — four in `tests/ir-schema.test.mjs` (9 → 13), three in
`tests/id-policy-content-policy.test.mjs` (19 → 22). The last of those walks every id issued
across a full regeneration, top-level and nested, and asserts the set size equals the count —
so it catches a duplicate arriving by any route, not only this one. Full suite 542 passing,
with the 4 pre-existing missing-package failures recorded in F-010.

**Still open, and not addressed here:** the uniqueness rule now lives in code with no
counterpart in `docs/CONTRACT.md`. §6 implies it (`idPolicy.preserve.elements` is a
name-keyed map) but never states it. Worth one sentence in §6's field notes so the next
person implementing an IR producer does not have to infer it from a validator.
