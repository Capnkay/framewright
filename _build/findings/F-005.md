## What is wrong

**`npm test` is red on `main`.** Two test files fail, and the repository's most-repeated
promise — that the suite runs on a fresh clone with **no `npm install`** — is no longer true.

```
✖ tests/mongo-store.test.mjs            Cannot find package 'mongodb-memory-server'
✖ tests/store-adapter-interface.test.mjs Cannot find package 'mongodb'
```

Two distinct causes, and the second is the serious one:

1. `tests/mongo-store.test.mjs` imports `mongodb-memory-server`. It is declared in
   `package.json` and `server/package.json` but not installed, so the file cannot load.

2. **`server/src/store/index.js:3` statically imports `./mongoStore.js`**, which imports
   `mongodb` at its top level. So *loading the store factory at all* requires the Mongo
   driver — even when the caller asks for the JSON store. `tests/store-adapter-interface.test.mjs`
   calls `createStore({ STORE_TYPE: 'memory' })` and never touches Mongo, and it still fails.

## Where

- `server/src/store/index.js:3` — `import { createMongoStore } from './mongoStore.js';`
- `tests/mongo-store.test.mjs:3` — `import { MongoMemoryServer } from 'mongodb-memory-server';`

Introduced by T-005. Verified by timing: the full suite was **42 passing, 0 failing** on a
branch based on `a0caef2`, and red immediately after pulling `main` with T-005, T-006 and
T-007. Re-verified by stashing all local work — both failures reproduce on a clean `main`.

## Why it matters

**This is not a missing-devDependency nuisance. Cause 2 is a Standing Rule 3 violation.**

> "The deterministic path always works. Any change that makes generation *require* an API
> key, a GPU, or a network is rejected." — `AGENTS.md`, and `docs/ROADMAP.md` Standing Rule 3

The JSON file store *is* the deterministic path — it is what runs with no Mongo, no network
and no services. A static import of the Mongo driver in the factory chain means that path
can no longer be selected without the driver present. T-003's own `doneWhen` says the
factory "selects Mongo or the JSON store from environment"; it currently requires both
regardless of the environment.

**And it breaks four documents that a new teammate reads first**, each of which states the
no-install promise as fact:

| Where | The promise |
|---|---|
| `SETUP.md` step 5 | "**This works right now, on a fresh clone, with no `npm install`.** Expect **13 passing, 0 failing**… If this fails on a clean clone, stop and say so before building anything on top of it." |
| `README.md` run table | "`npm test` — **works now — 13/13, no install needed**" |
| `docs/html/ONBOARDING.html` step 5 | "Expect 13 passing, 0 failing… If this fails on a clean clone, stop and say so" |
| `tools/test.mjs` header | "Zero dependencies, on purpose: `npm test` works on a fresh clone with no `npm install`, and this file must not be the thing that breaks that." |

The next person to clone this repository will hit a red suite at step 5 and, following the
instruction they were given, stop. `T-000`'s own `verify` is bare `npm test`, so it no longer
passes either.

## How to reproduce

From a clean checkout of `main`, with no `npm install` anywhere:

```
npm test                              # red: 2 files fail
npm test -- store-adapter-interface   # Cannot find package 'mongodb'
npm test -- mongo-store               # Cannot find package 'mongodb-memory-server'
```

To confirm it is not caused by local work:

```
git stash -u && npm test ; git stash pop
```

## Suggested fix

**Cause 2 — make the Mongo import lazy.** The factory should load `mongoStore.js` only on the
branch that actually needs it, so selecting the JSON store never touches the driver:

```js
export async function createStore(env = {}) {
  const type = env.STORE_TYPE || 'json';
  if (type === 'mongo') {
    const { createMongoStore } = await import('./mongoStore.js');   // only here
    return createAdapter(createMongoStore(env.MONGO_URI));
  }
  ...
}
```

That makes `createStore` async, which touches its callers — so an equally valid alternative
is to keep it synchronous and have `mongoStore.js` itself defer `require`/`import` of
`mongodb` until a connection is actually opened. Either shape restores the property that
matters: **the JSON path loads nothing Mongo-related.** Whoever owns it should pick; this
finding does not.

**Cause 1 — decide what `mongo-store` verification means with nothing installed.** Three
options, and it is a real decision rather than an oversight to paper over:

- Guard the test: skip with a clear message when `mongodb-memory-server` is absent, so the
  suite stays green on a fresh clone and still runs the real check on a machine that has it.
  `node:test` supports `{ skip: 'reason' }`, and a visible skip is honest where a silent pass
  is not.
- Install the dependency and accept that `npm test` now needs `npm install` — which means
  amending `SETUP.md`, `README.md`, `ONBOARDING.html` and `tools/test.mjs`, all of which
  currently promise otherwise. This is a real choice, but it should be made deliberately and
  written down, not arrived at by accident.
- Move Mongo coverage behind a separate script that is not part of `npm test`.

**Not fixed here.** Per `docs/REVIEW-PROTOCOL.md`, the reviewer takes the keyboard only when
a BLOCKER sits on the critical path **and** the owner cannot act. Antigravity owns T-003 and
T-005 and is currently active on T-071, so this is theirs. Flagged, not repaired.

**Unblocked in the meantime:** filtered verifications still work, because `tools/test.mjs`
selects by filename. `npm test -- app-shell` and `npm test -- job-store` both pass, so tasks
can still be completed against their own `verify` command while this is open. Only the bare
`npm test` is red.
