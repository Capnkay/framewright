## What is wrong

A nested card field's `css` has **nowhere to be stored**. §4's loop item shape defines
`fieldN`, `fieldTypeN` and `fieldIdN` and no `css` slot of any kind, and the hydration
reducer never writes a css entry for a nested id — yet four separate places in the contract
and the board require per-card css overlay to work.

Required by:

- **§5.0** — "The CSS-overlay rule (R10) has the same dependency: `allSectionsCss[pageName][fieldId]`
  is keyed by nested field ID too, so an unflattened store makes per-card styling silently
  impossible."
- **§7 R10** — apply `allSectionsCss` onto matching DOM ids after `cssData` changes.
- **T-014 `doneWhen`** — "a css value keyed to a nested card id is applied via `getElementById`
  after `cssData` changes."
- **T-053 `doneWhen`** — the side-editor's css overlay hook, validated client-side against §8.

Nothing in §4, §3 or §13.2 says where that value lives between the PATCH and the render.

## Where

- `docs/CONTRACT.md` §4 — loop item shape, no css slot.
- `client/src/redux/cmsSlice.js:79` — `css[el.fieldId] = el.css` is the **only** write to the
  css map, keyed by the element's own `fieldId`.
- `client/src/redux/cmsSlice.js:32-42` — `flattenLoopItemFields` writes into `allSections`
  only; it never touches the css map.
- `_build/tasks.json` — T-014 and T-053 require the behaviour.

## Why it matters

The css overlay is not a nice-to-have. It is named explicitly inside the **25-point CMS
compliance criterion**, and `docs/corrections/REGISTER.md` already records that the source
brief buries it under "stretch objectives" while grading it — "a team reading §4.3
deprioritises real points."

The failure mode is the one this project is most exposed to: the side-editor accepts a css
value for a card field, `PATCH /api/elements/3000000001` returns `200` with the parent
document, the store hydrates, and **nothing moves on screen** — because the value had no
slot to persist into and no key to hydrate under. Passes lint. Passes schema. Passes the §9
assertion, which patches nested `content`, not nested `css`. It surfaces when a judge styles
one card.

Discovered while reading §5.0/§5.2 to prepare the client spine, not by running a failing
test — there is no test for it yet, which is part of the problem.

## How to reproduce

```
node --input-type=module -e '
import { hydrateElements, initialCmsState } from "./client/src/redux/cmsSlice.js";
import { readFileSync } from "node:fs";
const els = JSON.parse(readFileSync("./seed/elements.json","utf8"));
const s = hydrateElements(initialCmsState(), els, "Home");
console.log("allSections keys :", Object.keys(s.allSections.Home).length);   // 13
console.log("allSectionsCss   :", Object.keys(s.allSectionsCss.Home));       // [ "2000000003" ]
console.log("css for 3000000001:", s.allSectionsCss.Home["3000000001"]);     // undefined
'
```

13 content keys hydrate, including all six nested card ids. Exactly **one** css key
hydrates, and it is an element-level id. Every nested id is `undefined`.

## Suggested fix

**Add optional `cssN` to §4's loop item, mirroring the existing `fieldN` naming.** Purely
additive, so it is legal under the change rule even after the clock starts.

```json
{
  "field1": "1000+",   "fieldType1": "Text", "fieldId1": "3000000001", "css1": null,
  "field2": "Community<br />Members", "fieldType2": "Text", "fieldId2": "3000000002",
  "css2": "font-weight: bold;"
}
```

Four small consequences, all of which fall out of rules that already exist:

1. **Reducer** — extend `flattenLoopItemFields` so that alongside
   `sections[item.fieldIdN] = item.fieldN` it also writes
   `css[item.fieldIdN] = item.cssN` when `cssN` is present and non-null. It already parses
   the `N` index out of `^fieldId(\d+)$`, so this is the same loop.
2. **API** — no new endpoint. §13.2 already resolves a `3…`-range id to its parent and
   updates that position inside the parent's `loop`, returning the parent's full document.
   `PATCH /api/elements/3000000001 {"css": "font-weight: bold;"}` writes `css1` on the item
   at that index. `null` clears the overlay, exactly as §13.2 already specifies.
3. **Sanitisation** — unchanged. §8's declaration allow-list applies at the same two
   chokepoints, and T-032's validator is reused as-is.
4. **Uniformity** — §4 rule 3 requires a uniform field count per item, recorded as
   `cards.fieldsPerItem`. `cssN` should be explicitly **exempt** from that rule: css is
   optional per field, and requiring a `cssN` for every field would force null padding for
   no benefit. Worth stating so nobody derives the opposite.

### Alternatives considered

| Shape | Why not |
|---|---|
| A per-element map, e.g. `loopCss: {"3000000001": "..."}` | Introduces a second addressing scheme inside one document and duplicates the id. §13.3 leaves orphaned card slots stored on shrink, so that map accumulates entries pointing at items no longer rendered. |
| A separate css/overlay collection | New store shape and a new endpoint, for a value that already travels with its element. §15.1 forbids caching element documents, so it buys no performance either. |
| Store nested css under the parent's key | Collides with the parent's own `css`, and cannot address two card fields differently — which is the entire point of the feature. |

**This is a contract change, so it is the team lead's call, not a reviewer's** — same rule
that governed F-001 and F-002. Proposed here rather than applied.
