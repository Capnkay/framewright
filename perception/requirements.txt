# Framewright perception service — CONTRACT.md section 12.
#
# Install into a dedicated virtual environment, NOT the system interpreter, and
# build that environment on PYTHON 3.10 -- see the version note below.
#
#     py -0p                      # list the interpreters you actually have
#     <path-to-python3.10> -m venv perception/.venv
#     perception/.venv/Scripts/python -m pip install -c perception/constraints.txt #         -r perception/requirements.txt                                        # Windows
#     perception/.venv/bin/python  -m pip install -r perception/requirements.txt      # POSIX
#
# WHY 3.10 AND NOT WHATEVER `python` RESOLVES TO. torch's cu124 wheels are built
# per CPython version. The wheel this project uses is cp310 -- CPython 3.10 and
# nothing else. `python -m venv` picks the first `python` on PATH, which on the
# build machine is 3.14, and there is no cu124 wheel for it. Verified on
# 3.10.11.
#
# THE GPU BUILD IS NOT LISTED HERE, DELIBERATELY. torch's CUDA wheels do not come
# from PyPI, so `pip install torch` silently installs the CPU build and /health
# then reports "cpu" on a machine that has a perfectly good GPU. Install it
# explicitly first, from the index in docs/GPU-BENCHMARK.md:
#
#     perception/.venv/Scripts/python -m pip install torch --index-url https://download.pytorch.org/whl/cu124
#
# Check for a cached wheel first -- gpu-test/ already holds
# torch-2.6.0+cu124-cp310-cp310-win_amd64.whl, and installing from that file
# skips a 2.5 GB download.
#
# ALWAYS PASS -c perception/constraints.txt. Installing ANY package that depends
# on torch lets pip resolve it from PyPI, where the only wheel is the CPU one --
# `pip install transformers` has already destroyed a working CUDA install here
# once. See docs/EDGE-CASES.md EC-013.
#
# Then verify before anything else: GET /health must report cuda:0 (roadmap gate
# 0.7). If it says cpu, you are on the wrong interpreter or the wrong wheel. See
# docs/EDGE-CASES.md EC-012, which is the full account of getting this wrong.
