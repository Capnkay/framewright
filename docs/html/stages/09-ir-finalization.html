Semantic Planning & IR Generation

IR Finalization

Assemble the complete IR, validate it against the schema, and only then hand it on.

IN

Layout, cards and elements from Cards 6-8, plus irVersion, pageName, source, idPolicy from the request.
→

OUT

One Ajv-validated IR document, handed to the Node API for ID allocation.

What it actually does

This is the last stop before anything gets an ID. Layout, theme, cards and elements from the three prior cards are assembled into one object, together with the fields Node already knows — irVersion, pageName, sectionName, source, idPolicy (§12: "there is no irFragment"). The whole thing is checked against the IR's Ajv schema before it goes anywhere else. Only a valid IR is handed to the Node API, which is the only place a fieldId is ever minted.

Out

// the complete IR, Ajv-validated — no fieldId anywhere (§1, §6)
{
  "irVersion":   "1.0",
  "sectionType": "split-hero",
  "pageName":    "Home",
  "layout":      { ...from Card 7... },
  "theme":       { ...accent, surface, text, textMode... },
  "cards":       { ...from Card 8, or null... },
  "elements":    [ ...from Card 6, order from Card 7... ],
  "idPolicy":    { "mode": "allocate", "contentPolicy": "overwrite" },
  "variations":  "1",
  "warnings":    []
}

Why validate before allocating IDs

ApproachVerdictReason
Validate-before-allocatechosen Allocating IDs for an IR that later fails validation leaves orphaned sectionId / fieldId counter values — burnt numbers that never map to a real element, and §1's atomic-counter guarantee makes them unrecoverable.
Allocate first, validate afterrejected Ties validity to a side effect that already happened. A caught error still leaves IDs allocated and unused.
No finalization step — Python's raw response is the IRrejected §12: "there is no irFragment." Node must assemble the whole IR from the response's named sub-objects plus request-supplied fields — skip that and a partial object ships as if it were complete.
No fieldId appears anywhere in the IR. A model that emits one is producing invalid IR, and the validator rejects it — IDs are allocated by the API, after this stage, never before it.

How it fails

FailureWhat happens
Missing CTA or headingNever a silent drop. Recorded in warnings, matching §6's warnings: [] array and the API response's warnings field (§13).
An IR that validates but is nonsense
e.g. zero elements		Unverified. Ajv checks shape, not sense — whether the schema enforces a minimum element count is a real gap between "valid JSON" and "usable section."
Version driftThe contract is frozen at "1.0" (top of file: Status FROZEN, Version 1.3). A mismatched irVersion means a stage is running stale code; §6 states no automatic migration.
Node's assembly disagrees with Python's response§12: Node takes irVersion, pageName, sectionName, source, idPolicy from the request and everything else from the response. Miss one and the IR ships a stale request-side value instead of the fresh perceived one.

What it must not break

  • §6 — the IR is the bridge; every field named there must be present and correctly typed, or nothing downstream can read it.
  • §1 — no fieldId anywhere in the IR; only the API allocates IDs, and only after this stage.
  • §11 — the IR is the artifact stage 4 persists; the trace's outputRef points at it, and replay reads it back.
  • §12 — there is no irFragment. Node assembles the IR from the response's named sub-objects, never a single opaque blob.
