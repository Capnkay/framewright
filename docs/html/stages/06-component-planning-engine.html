Component Planning Engine

Turn a detected region into a named, typed element from the fixed reference set.

IN

Detected regions with roles, text and confidence, from stage 5.
→

OUT

Elements matched to the reference set — a name, a contentType, an HTML tag.

What it actually does

The reference set (§3) is seven names, each with a fixed contentType and HTML tag already decided by the brief. This stage's whole job is matching: given a region's role, size and position, which of the seven does it become? A large bold line near the top matches headlineMain — not because of its font size, but because nothing else in the seven-name table fits a short, prominent line of text better. Once matched, contentType and the tag are read straight out of §3, never invented.

Out

// one entry per matched element — order and css are not decided here (§6)
{
  "elementName":  "headlineMain",
  "contentType":  "Text",
  "tag":          "h1",
  "confidence":   0.94,   // carried from stage 5
  "sourceOf":     "wireframe",
  "bbox":         [500, 80, 350, 60]
}

Why a fixed reference set, not free-form names

OptionVerdictReason
Fixed 7-name set
heroImage, brandBadge, headlineMain, headlineSub, description, statBadges, ctaButton		chosen §3's table is exhaustive for the split-hero. The rubric grades the generated component against these exact keys, so a judge who knows the brief can search for headlineMain and expect to find it.
Free-form region naming
"topText", "mainHeading"		rejected Nothing downstream — the const ids map, the CMS records, the judge's checklist — agrees on a name the model just invented. Two runs of the same wireframe could name the same region two different things.
contentType from box size alonerejected A large image and a large text block are both "big boxes." Size can't tell Image from Text apart — the match has to go through the matched elementName, which already carries its type in §3.
contentType decided later, at generationrejected Stage 5 reads the IR and never sees the wireframe again. Leave contentType undecided here and two variations of the same section could render the same region as an <img> in one and a <p> in the other.
This stage never invents a name. A region that matches none of the seven falls through — to a lower confidence band (§10) or the deterministic template — rather than being force-fit into the nearest guess, because a wrongly-named element breaks the const ids map that every later stage depends on (R1).

How it fails

FailureWhat happens
Two regions both look like the headlineOnly one wins headlineMain. The other must resolve to a different name in §3's table, or drop below the confidence band and escalate (§10).
A region with no matching roleNot force-fit. Recorded unmatched; falls to the deterministic template or a warning (§10, §11.3 if review is on).
A wireframe box outside the seven names
e.g. a testimonial quote		Unverified. §3's set is scoped to the split-hero brief. Nothing states what happens to a genuinely new region type.
contentType mismatchWrong tag downstream — the generated component renders an <img> where a <p> was meant, or the reverse.

What it must not break

  • §1 — this stage never allocates a fieldId. Elements come back identified by name and position only.
  • §3 — the reference element set is exhaustive for this section type; a name outside it breaks const ids (R1) and every CMS lookup after it.
  • §6 — contentType must be one of the five closed values (Image | Text | Textfield | Button | Cards); anything else fails Ajv at Card 9.
  • §11 — this stage's decisions are one immutable trace record. A retry appends; it never overwrites.
