Multi-Modal Understanding

Confidence Scoring

Every element carries a number, or an honest null — never a guess dressed up as one.

IN

An element from any source, with its raw model score if it has one.
→

OUT

The same element, banded — accept, verify, or escalate — and surfaced in the API and the Glass Box.

What it actually does

The band is the same three-way split whatever produced the score — a vision model's box, a code parse, or a prompt extraction. Only vision output ever has a real number; code and prompt sources carry null, because nothing scored them. The band, the score and the triggering warning are all written into the job's stage trace, so a judge can see exactly why an element was accepted, flagged, or held for a human.

Out

// the only field this stage adds is "confidence" (§6) — same shape whatever produced the element,
// null when it never came from an image. "band" and "action" below are not IR fields; they show
// what the number means, not what gets stored.
{
  "elementName": "headlineSub",
  "confidence":  0.43
}
// 0.43 falls under 0.60 → band: escalate (§10)
// review opted in → job.status: "awaiting-input" (§11.3); otherwise falls through to the template

Which bands, and why that split

OptionVerdictReason
Three explicit bands
§10: ≥0.85 / 0.60–0.85 / <0.60		chosen Keeps a "verify but don't block" middle case distinct from both a clean accept and a hard escalation.
Single thresholdrejectedToo blunt — collapses "almost certain" and "borderline" into the same accept/reject line, throwing away the middle case entirely.
Fabricated number for non-image sourcesrejectedCode and prompt elements were never scored by anything. null is honest; a made-up 1.0 is not.
The dangerous failure isn't a low score — a low score gets caught by design. It's confident and wrong: a high number attached to the wrong role or the wrong text. A band can only reduce blast radius; it can't detect its own miscalibration. Only a golden-file diff, or a human, catches that one.

How it fails

FailureWhat happens
Confident and wrongAccepted at ≥0.85, no warning raised. Only the golden-file diff catches it.
All elements cluster mid-bandUnverified. Nothing in the contract caps how many elements can sit in "verify" at once; whether that overloads a human reviewer at demo scale is untested here.
Model exposes no calibrated confidenceFabricating a number is forbidden — the element carries null, same as any non-image source. Honest, but loses the accept/verify/escalate split entirely for that element.
Perception service downVision-based scores are unavailable; that stage is marked degraded (§11.1). Code- and prompt-sourced elements still carry their own null as normal.

The bands, exactly (§10)

≥ 0.85accept — use directly
0.60–0.85verify — second-pass check, record a warning
< 0.60escalate — ask a human, or fall through to the template

What it must not break

  • §10 — the three bands and their exact thresholds and behaviours; nothing rounds or collapses them.
  • §6 — every element carries a confidence field, 0.0–1.0 or null, never fabricated for a non-image source.
  • §11.3 — an element below 0.60 pauses the job at awaiting-input only if the studio opted into review; otherwise it falls through to the deterministic template with a warning. A headless run never blocks on a human who isn't there.
