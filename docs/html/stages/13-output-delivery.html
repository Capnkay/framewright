Output & Delivery

Output & Delivery

Persist the section, persist its elements, write the component, and hand back a response a judge can act on.

IN

A validated IR, its generated component file, and the CMS documents it produced.
→

OUT

A persisted section + elements, a written .jsx file, and the { ok, ... } response — plus a ZIP on request.

What it actually does

The section row is written first, then its elements, then the component file — in that order, deliberately. If anything fails partway, the world is left with a section that has no elements yet, which is harmless and re-runnable, never with elements pointing at a section row that does not exist. The API response carries the IDs, the component path, and any warnings; the ZIP export reads what is already persisted, not a separate code path.

Write order, and why it runs that way

OptionVerdictReason
Section row first, then elementschosen A partial failure orphans a section with no elements — harmless, easy to retry or discard.
Elements first, then the section rowrejectedA partial failure orphans elements with no parent section — those fieldIds are allocated, stored, and unreachable, corrupting the ID space §13's atomicity rule forbids exactly this.
Regeneration allocates fresh IDsrejectedBreaks the one thing the demo depends on: idPolicy.mode is forced to preserve on regenerate (§13.3) so a judge's own typed content survives a design change.
Regeneration forces contentPolicy: "keep". A judge types their own headline, the design changes underneath it, and their words survive — because the field kept both its ID and its content (§6, §13.3). That single behaviour is the entire demo.

How it fails

FailureWhat happens
Partial write (section written, elements fail)Section exists with no elements — harmless per the ordering choice above; safe to retry.
Two jobs target the same pageNameID allocation is atomic and centrally counted (§1, §2.1); a read-modify-write counter would issue duplicates — the pre-submit gate checks for exactly that.
PATCH on a nested card IDMust resolve to the parent element and update that position in loop, returning the parent's full document — not 404 (§13.2).
ZIP containing something that must never leave the repoReal keys, hosts, ObjectIds, absolute local paths, or model weights (§14) — the export is built from the same source the pre-submit gate scans.

What it must not break

  • §13 — every endpoint's wire shape, including the envelope convention: actions return { ok, ... }, collections return a bare array, single documents return the bare document or 404.
  • §13.2 — a PATCH on a nested (3…-range) field ID resolves to its parent element and returns the parent's full document; it does not 404.
  • §13.3 — regeneration keeps the sectionId, forces idPolicy.mode: preserve, and content follows contentPolicy: keep.
  • §11.2 — artifacts are owned by Node, retrieved by GET /api/jobs/:jobId/artifacts/:name; the Python service never writes them.
  • §14 — nothing in the ZIP or the response may contain a real key, host, ObjectId, absolute local path, or model weight.
