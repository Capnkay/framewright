Semantic Planning & IR Generation

Layout Planner

Decide the spatial structure — direction, breakpoint, regions, and the order inside each.

IN

Named elements from Card 6, with their source positions.
→

OUT

A layout object — regions, sides, container, accents — and an explicit order per element.

What it actually does

Two candidate orderings exist for the same elements: where a box sits in the picture, and what the prompt says should come first. Both are legitimate and they will not always agree, so this stage is the one place that reads both, picks a winner per §6's conflict order, and writes the result down as an explicit order field on each element. It also decides direction, breakpoint, which region sits left and which right, and the container and accent bars. Everything after this reads order and never recomputes it.

Why an explicit order field

ApproachVerdictReason
Explicit order, decided once
written onto each element in this stage		chosen §6, verbatim: ordering derived from a bounding box at read time and ordering derived from a prompt at read time will not agree — so it is decided once, here, and written down.
Order derived from bbox y at render timerejected Works alone, but breaks the moment a prompt override reorders the same section — bbox order and the prompt's stated order can disagree live, with no rule for which wins.
Order derived from array position at render timerejected Regenerating a section can return elements[] in whatever sequence the model emitted them, which is not necessarily reading order.
order is decided exactly once, here. A bounding box read at generation time and a prompt read at generation time can each justify a different position — so nothing downstream is allowed to derive order on its own; it obeys what this stage already wrote.

How it fails

FailureWhat happens
A three-column wireframe§6's model has exactly two regions, media and content (also R11). A third column has no region to hold — its children fold into one of the two, and which one is unverified.
Overlapping regionsUnverified. §6's schema records side and width per region but has no stated overlap check.
Mobile order differs from desktopIR v1.0 models one order per element, not one per breakpoint. mobileBehaviour: "stack" reuses the same order — a design wanting a different mobile order isn't representable.
An unmodelled breakpoint valueUnverified. §6's example only shows "md"; no closed enum for breakpoint is stated.

Layout defaults (§6, R11)

directionrow
breakpointmd
mobileBehaviourstack
columnstwo, desktop only

What it must not break

  • §6 layout object — direction, breakpoint, mobileBehaviour, container, regions, accents. Stage 5 reads this literally; nothing there is inferred.
  • §6 order field — decided once, obeyed by generation. Recomputing it elsewhere reopens the exact disagreement this field exists to prevent.
  • §7 R11 — two columns on desktop, stacked on mobile, inside a max-width container. A layout that violates this fails the generated-component rule directly.
  • §11 — layout is persisted as an artifact, so Card 9 and a human replay from stage 4 can read exactly what this stage decided.
