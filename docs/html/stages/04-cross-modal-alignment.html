Multi-Modal Understanding

Cross-Modal Alignment

When wireframe, code and prompt describe the same section and disagree, decide — out loud.

IN

Up to three IR fragments — wireframe, code, prompt — for one section.
→

OUT

One merged IR, each field's winner recorded in sourceOf, every override in warnings.

What it actually does

Only fields that two or more sources both describe go through resolution — a field only one source mentions is simply kept, with sourceOf set to whichever supplied it. For a genuine conflict, §6's order decides: prompt wins copy, colour, CTA and card count; wireframe wins spatial layout, order and alignment; code wins technical patterns — selector shape, helper names, class conventions.

Out

// excerpt from the merged IR — wireframe said red-500, prompt said green, prompt wins colour per §6
{
  "elements": [
    { "elementName": "ctaButton", "classes": "bg-green-500 text-white", "sourceOf": "prompt", "confidence": 0.81 }
  ],
  "warnings": [
    "ctaButton colour: prompt overrode wireframe (green-500 vs red-500), per §6"
  ]
}

How it decides

ApproachVerdictReason
Explicit priority order
§6: prompt / wireframe / code, by field domain		chosen Fixed and named per field domain — anyone can predict the winner before running it, and every firing is logged.
Last input winsrejectedOrder-dependent on which upload finished processing first. Not reproducible, and silently favours whichever track happened to run last.
Ask a model to reconcilerejectedUnauditable — nobody can point to why field X won without re-asking the model, and it may answer differently next time.
Every time the priority rule actually fires — a real disagreement, not just one source being silent — it is written to warnings. That's what makes the resolution auditable instead of assumed: a judge (or a later stage) can see exactly which field was overridden, by what, and why.

How it fails

FailureWhat happens
Two sources at equal priorityShouldn't occur by design — every field domain has exactly one deciding source. If it does, that's a bug in the domain mapping, not a case this stage is built to arbitrate.
Present in one input, absent from the othersNo conflict. Kept as-is, sourceOf set to whichever input supplied it.
Silent resolution, no warningThe dangerous one — a merge happened but left no trace of it. Only a golden-file diff against expected warnings catches it.

The priority order, in one line each

  • Prompt — copy, colour, CTA behaviour, card count
  • Wireframe — regions, order, alignment
  • Code — selector shape, helper names, class conventions

What it must not break

  • §6 conflict order — the three-way priority is fixed by field domain, not negotiable per section or per run.
  • sourceOf — set to whichever source's value actually survived into the merged IR, never left blank and never set to something like "combined".
  • warnings — every override the rule actually applies gets one entry; a field that only one source described is not an override and gets none.
