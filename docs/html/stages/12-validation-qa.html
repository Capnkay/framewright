Validation & QA

Validation & QA

Three independent checks a generated component must pass, because each catches what the other two cannot.

IN

A CMS document set and a generated .jsx component, plus the IR it was generated from.
→

OUT

Pass, or an error report and a bounded regenerate-then-fallback.

What it actually does

Ajv checks the CMS documents against their schemas — shape only. ESLint runs against the generated JSX hermetically, resolved from a fixed inline config rather than anything derived from the input, because a config path built from user data is code execution at lint time. A third, structural check walks the component and the IR side by side: every IR element present, every fieldId in the tree, every nested card ID in the mount-time fetch. A failure regenerates with the error report attached, bounded, then falls back to the deterministic template.

Out

// structural check result
{
  "schemaOk":     true,
  "lintOk":       true,
  "structuralOk": false,
  "errors": [
    "nested fieldId 3000000004 missing from mount-time fetchElementsByIds call"
  ]
}

Three checks, not one

OptionVerdictReason
Three independent checkschosen Schema catches shape, lint catches syntax, structural catches semantics against the IR — none of the three can see the other's failure mode.
A single "does it look right" model checkrejectedUnauditable — no error report to regenerate against, and it cannot prove a negative, such as a nested ID missing from the fetch.
Structural check alonerejectedWould miss a schema violation in the seed CMS data itself, and a syntactically broken component the parser cannot even walk.
Valid JSX can be perfectly wrong. A component can compile, lint clean, and pass schema validation — and still have a dead store, because every field falls back to its hard-coded default (§9). Only the structural check plus the §9 store-liveness assertion — patch a value, watch it move — catches that.

How it fails

FailureWhat happens
Schema too strict for the organiser's own seed dataThe seed data is ground truth (§2); a schema that rejects it is the bug, not the data.
Regeneration loopsRetries are bounded; exhausting them falls back to the deterministic template rather than looping forever.
Passes lint, semantically deadEvery field renders its hard-coded default, store never hydrates. Passes schema, passes lint, fails §9 step 5.
Hermetic config resolved from an input-derived pathA config path built from the upload or prompt is code execution at lint time (§8) — the config must be a fixed inline object.

What each check can and cannot see

Ajvshape, types, enums
ESLintsyntax, dead imports
Structuralmissing elements/fieldIds, unflattened cards

None of the three can see what only the §9 assertion catches: a store that never moves.

What it must not break

  • §9 — the store-liveness invariant and its five-step assertion; step 5 (patch a nested card field, assert it moves) is the one a DOM-presence check alone cannot fake.
  • §7 — every rule the structural check verifies against the component.
  • §3 — the element document shape the schema check enforces, including the contentType enum and loop required only for Cards.
  • §8 — hermetic ESLint: a fixed inline config, never one resolved from an input-derived directory.
