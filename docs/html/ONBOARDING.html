Framewright  ·  read this once, on day one

Your first hour

Twenty minutes of reading, ten minutes of setup, then you are building. Everything else arrives when you need it.

Part 1 — Get your machine working (10 min)

1
Clone and enter 
git clone <repo-url> framewright
cd framewright
2
Turn the safety gates on — do not skip this 
git config core.hooksPath .githooks

This is per-machine and nothing sets it for you. Without it you get no secret scanning, no integrity checks, and no commit gates — silently, while everything appears to work. If you forget, the board will shout at you the next time you run it.

3
Tell the tools who you are 
echo "Your Name" > _build/.me
git config user.name "Your Name"
git config user.email "you@example.com"

Your name goes on your claims and your journal. Use the same one everywhere.

4
Make your own environment file 
cp .env.example .env

.env is ignored by git and must never be committed. .env.example is committed on purpose and contains only placeholders.

5
Prove it works 
npm test

Expect 13 passing, 0 failing. No npm install needed — these checks are zero-dependency on purpose. If this fails on a clean clone, stop and say so before building anything on top of it.

6
Look at the board 
node tools/baton.mjs status

Who holds what, what is blocked, what is next. If you skipped step 2, this is where you find out.

Part 3 — Every session after that

Type: continue build

That's the whole thing. It pulls, shows you the board, hands you the next task whose dependencies are met, and tells you which contract sections that task must satisfy. You claim it, build it, mark it done — a verification runs and decides — then commit with the task id and push.

Doing it by hand instead? node tools/baton.mjs status → next → claim T-0xx → build → done T-0xx. Full protocol and every failure case: docs/BATON.md.

Part 4 — The tracks

Nobody splits until the spine is green. Phases 1 and 2 are everyone, together, on the contract and the first working round-trip. The split happens at Phase 3, around hour 17.

Studio & Preview — 1 person

Owns: the Generator Studio — upload form, code and prompt inputs, mode selector, accent colour, plain-language errors, job history, the read-only generated JSX view. Plus the preview shell, the CMS side-editor, responsive toggle and CSS overlay.

Needs: React, forms, Tailwind, a good eye for error states.

Worth 10 points on its own, and it is the surface a judge touches first.

Generation — 2 people

Owns: prompt→IR and the keyless fallback, code→IR via AST, cross-modal alignment, the three planners, IR finalisation, and the deterministic emitter.

Needs: Node, careful thinking about data shapes, comfort with prompt engineering and with writing a small compiler.

Eight of the thirteen subsystems. This is the largest track, which is why it has two people.

API & Glass Box — 1 person

Owns: every endpoint, the ID allocator, job records and stage traces, the Job Timeline UI, replay, regeneration, the model orchestrator, zip export.

Needs: Node/Express, data modelling, a taste for making systems inspectable.

The Timeline is what makes our process visible to a judge instead of claimed.

Perception — 1 person (the GPU machine)

Owns: the Python service — image normalisation, rectangle and contour detection, OCR, fusion, spatial hierarchy, and the IR fragment it returns. Then the synthetic wireframe generator that trains a detector on data we render ourselves.

Needs: Python, OpenCV, patience with environment setup.

Everything else must work without you. That is by design, not an insult — it is what lets you experiment freely.

A sixth person floats: code-input mode first (pure AST, no GPU, and half of the input-coverage criterion), then wherever a track is behind. If we are five, the float folds into Generation.

Part 5 — Four things that will cost us if you get them wrong

1. The store has to be alive

Every field renders as value || "DEFAULT". With a dead data store the page looks identical to a working one. It only fails when someone changes a value and nothing moves — which is exactly what a judge is told to do. Caps us at 40/100. An automated check catches it; never disable it.

2. Some code looks wrong and is graded

Do not tidy dangerouslySetInnerHTML, the dynamicStyle / dynamicStyle2 classes, the const ids map, or CSS applied via getElementById. Every one is inspected. Tidying them costs 25 points.

3. The contract is the spec, not the task title

Your task names the sections it must satisfy. Open them. Building from the title is how the contract gets broken by someone who believes they are complying.

4. Claim before you build

One person per task. Two people claiming the same one causes a git conflict on purpose — that is the collision surfacing instead of hiding. And never mark a task done because it looks right; the verification decides.

What happenedWhat to do
Your session died mid-taskYour claim stands with a timestamp. Reclaim it, or let someone takeover
Two of you claimed the same taskGit conflicts on the claim file. Talk, keep one, the other runs baton next
Your work went stalenode tools/baton.mjs sync tells you if something that landed affects your task. Silence means nothing relevant moved
A hook blocked something legitimateFix the hook and log it. Never weaken or disable one to get past it
Something behaved surprisinglyCheck docs/EDGE-CASES.md first — it may already be there. If not, add it while it's fresh
You disagree with the contractYou may be right. Fix the contract and log it in docs/corrections/REGISTER.md. Never diverge quietly in code
