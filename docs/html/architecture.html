Architecture

Seven stages, thirteen subsystems, four supporting layers

Every box below is either a contract section or a stage card. Nothing here is aspirational — where the original hand-drawn diagram named a component we cannot use or had not scheduled, this page says what we actually build and why.

What changed from the original diagram. Stage 3 named LayoutLMv3, Donut and YOLOv8. All three are out — one is AGPL with a network clause our architecture triggers, one ships non-commercial weights, and one emits text where we need coordinates. The real stack is below, and it was chosen on a measurement, not a preference. See card 1 and the benchmark.

The four supporting layers

Added to the contract as §15–§18 in v1.5. Every one is optional and every one has a named fallback that needs no environment at all, because Standing Rule 3 says the deterministic path always works. The demo runs with all of them switched off — T-078 asserts exactly that, in a single rehearsal.

Data layer

§2.1 store · §15.1 cache
  • Section & element store — Mongo or a JSON file store behind one interface. allocateId is the only ID source and must be atomic
  • Cache — in-process TTL map by default; Redis when REDIS_URL is set and reachable. Unreachable warns once and falls back
  • Four cacheable keys only: ir:, render:, embed:, perceive:
  • Elements and sections are never cached. A cache in front of the live store reopens the exact §9 failure — the PATCH lands, the store is right, the preview does not move

ML / AI services

§16 · card 10
  • Model orchestrator — every hosted call goes through callModel. One retry on timeout or schema failure, never on a 4xx. Output validated against Ajv before it is returned
  • Embeddings + reranker — embed() returns null with nothing configured; callers fall back to the §6 keyword scorer. rerank() falls back to lexical overlap and is always callable
  • No key means no network attempt — { ok: false } immediately. A supported state, not an error
  • Model output is untrusted input: schema-validated, then sanitised write-side per §8

Storage layer

§11.2 · §13.1 · §15.2
  • Local disk by default — uploads/<jobId>.<ext> and artifacts/<jobId>/<stage>-<name>.<ext>
  • S3 / MinIO optional — same keys, different backend, so a stored outputRef resolves under either
  • Artifacts are owned by Node. The Python service never writes a file — it returns stage outputs inline and Node persists them, because a relative path written on the GPU laptop resolves to nothing anywhere else
  • Reads are proxied through VITE_STORAGE_URL, trailing slash intact. A bucket host in a response body is a §14 and R13 violation

Observability

§17
  • Logs — one JSON line per event. Subject to §14 in full: an upload is logged as its <jobId>.<ext> key, never the user's original path
  • Metrics — GET /api/metrics in Prometheus text format. The endpoint is the contract; scraping it is optional and no server is required
  • Tracing — one span per stage, names matching §11.0 exactly. Dropped silently with no collector configured
  • Alerts — out of scope. /api/health is the liveness surface; the job's status is the failure surface. Nothing pages anyone
The one sentence. We do not ask a model for a webpage. We convert inputs into a validated structured representation, then generate React and CMS metadata from it, and validate both independently — which is why the whole thing still runs with the GPU off, the key unset and the network down.
