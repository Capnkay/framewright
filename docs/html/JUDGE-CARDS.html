The one-sentence pitch for the whole system

We do not ask a model for a webpage. We convert a wireframe, a prompt, or pasted code into a validated intermediate representation, then generate a React component and its CMS metadata from that representation, and validate both independently. (docs/ROADMAP.md, the demo script's opening line)

Why an IR exists at all, rather than asking a model for a webpage directly

"The IR is the bridge. Perception writes it, generation reads it, validation compares against it, and the Glass Box replays from it." (§6) A model asked for a webpage directly gives you one opaque answer with no seam to test, replay, or recover from. An IR gives every stage a persisted input and a persisted output — which is what makes each stage independently testable, and what makes a bad stage-3 guess correctable by replaying from stage 5 without repeating perception. (§11, docs/VERIFICATION.md)

What "CMS-bindable" means, and why it is 25 of 100 points

Every editable node in the generated component carries an id that is a real, persisted fieldId, wired to state.cms.allSections[pageName] in Redux (§5, §7 rules R1/R3/R4/R5). "CMS-bindable" means a judge can open the DOM inspector, find that id, then PATCH it, and watch the exact text they typed appear in the preview with no refresh. It is the single largest line item in the scoring rubric — CMS contract compliance is worth 25 of 100 points, more than any other criterion. (docs/ROADMAP.md scoring table)

The honest limitation we volunteer before being asked

Every text node renders as data?.[id] || "DEFAULT". That fallback is also a mask: a completely dead store renders pixel-identical to a live one — right copy, right layout, right responsive behaviour. It compiles, lints, and passes schema checks. It only fails when someone changes a value and the preview does not move — which is exactly what we ask a judge to do at the demo's central moment. (§9, verbatim reasoning)

Studio & Preview

Takes in →the operator's chosen mode (wireframe upload, pasted code, or a typed prompt), plus display preferences (accent colour, layout mode, responsive toggle).
Emits →a live, editable preview of the generated section, a read-only view of the actual generated JSX, and a job history — all wired to the same store a judge can edit directly.
A judge will askThe honest answer
"What happens if I upload a file that's too big or the wrong type?" A plain-language error in the form, not a stack trace. Over 8 MB is 413; anything other than PNG/JPEG/WebP is 400 (§13.1) — the form surfaces both as text a non-engineer can read, which is one of the studio's own nine numbered requirements.
"Can I actually see the code you generated, not just the rendered result?" Yes — a read-only JSX view, backed by GET /api/jobs/:jobId/component (§11.2), which exists specifically because the generate response only returns a path, and a judge is entitled to see the source, not a static mount someone invented later.
"What happens if the hosted model call fails or you have no API key?" The studio keeps working. A keyless prompt path extracts section type, card count, accent colour and CTA label straight from the typed text into the same IR and the same deterministic emitter — no model call at all (docs/ROADMAP.md Phase 2's keyless gate).

The number I should have ready

How many of the nine numbered Generator Studio requirements (FR-G01–FR-G09) are actually implemented, out of 9 — the studio is scored as its own 10-point line item, not folded into "the app works." (docs/ROADMAP.md Phase 3)

What to say when something fails live

Name the deterministic fallback and let it run in front of them — "that's the keyless path, watch it produce the same shape without the key" — rather than apologising or quietly retrying the same failing call. If the form itself is unresponsive, switch to the recorded backup run (docs/ROADMAP.md Phase 5) and say so plainly.

API & Glass Box

Takes in →a generation request, a replay request, or a regenerate request.
Emits →a persisted job record with an append-only trace of all seven pipeline stages (§11), queryable by stage, replayable from any point, and exportable as a zip.
A judge will askThe honest answer
"How do I know the store is actually alive, not just rendering hard-coded defaults?" Type a value into a top-level field and watch it change, then do the same to one nested card field. Both have to move — a DOM-presence check alone would pass on a completely dead store, because the default constants put the right ids in the DOM with no data behind them (§9, steps 4–5).
"What happens if the GPU laptop or the perception service is down right now?" The affected stage is recorded as degraded, a warning is attached, and the job still succeeds down the deterministic path — degraded is "a success for the job and a warning for the stage" (§11.1). Prompt and code mode never depend on it (§12).
"If I regenerate with a different design, do I lose the headline I just typed?" No. Regeneration forces idPolicy.mode: preserve — every element whose name is unchanged keeps its existing fieldId, and therefore its content (§13.3, rule 2: "the whole demo").

The number I should have ready

End-to-end contract pass rate — of N generated sections, how many produce a fully compliant component against every §-numbered rule in one pass, not just "it rendered." (docs/VERIFICATION.md, metrics table)

What to say when something fails live

Open the Job Timeline and point at the failed or degraded stage — it is visible, not hidden, by design. Then replay from stage 5 with the corrected input. This is the rehearsed recovery beat, not an improvisation: "a pipeline that recovers visibly from a failure is more convincing than one that never fails in front of you." (docs/ROADMAP.md, the demo script's own words)

Perception

Takes in →a normalised wireframe image and the label set we are looking for.
Emits →labelled regions — role, position, text, and a confidence score per region — with zero training and no fieldId ever allocated (§1, §12).
A judge will askThe honest answer
"Why Florence-2 and not YOLO or a general vision model?" Open-vocabulary grounding needs zero training for a label set nobody trained a model on — hand it the phrase "call to action button" and it returns a box. YOLOv8 has no UI classes at all and its AGPL licence has a network clause our architecture triggers; LayoutLMv3's published weights are non-commercial. Neither can even attempt our label set without retraining.
"Have you actually tested this on hand-drawn wireframes, or just clean screenshots?" Stated plainly: unverified until the Phase 0.8 benchmark ran. Every published Florence-2 result is on rendered screenshots or photographs; hand-drawn boxes are our real input, and nobody had published a number for that before we measured it ourselves.
"What happens when the model gets it wrong?" Confidence bands decide the behaviour, not a guess: ≥0.85 accept and use directly, 0.60–0.85 verify with a recorded warning, <0.60 escalate to a human or fall through to the deterministic template (§10).

The number I should have ready

Element recall against the hand-labelled fixture set — of the regions that are really in the wireframe, how many did we find. Fifteen labelled wireframes beat a thousand unlabelled ones. (docs/VERIFICATION.md, "the honest answer to 'does perception work?'")

What to say when something fails live

Call it degraded, not broken — that is the actual status the trace records, and it is a deliberate part of the contract, not a euphemism. Show the low-confidence question in the human-in-the-loop prompt, answer it live, and replay from stage 5. A visible recovery from a real perception miss is a stronger demo than a perfect run nobody can trust.

Everyone

Takes in →every change any track makes to this repository, regardless of who wrote it or which track they own.
Emits →either a clean, secret-free, contract-compliant commit — or a blocked one. There is no third option.
A judge will askThe honest answer
"What actually stops a real API key from reaching your public repo?" Two write-time hooks, a commit-time secret scan, and a push-time scan over full git history — because a key deleted in a later commit is still a leak the moment the repo goes public. All five checks are named in docs/THREAT-MODEL.md, item 7 (Secrets).
"You used an AI coding tool to help build this. What stops it from disabling your own safety checks?" A SHA-256 manifest (LAW-MANIFEST.sha256) covers every hook, .gitignore, and the git hooks themselves, verified on every commit. Stated honestly: this is a commit-boundary control, not a sandbox around the tool itself — see docs/THREAT-MODEL.md, item 9 (the orchestrated-executor surface).
"Why doesn't your 'works with no key, no GPU' claim just mean the demo is worse?" Because the deterministic path is not a degraded mode — it is a separate, equally real code path: keyword extraction into the same IR schema, through the same emitter, producing a compiling, CMS-bound component. It is exercised on every commit, the same as the model-backed path.

The number I should have ready

Zero secrets in full git history, zero field IDs outside the sanctioned ranges, zero duplicate IDs — the pre-submit gate's own pass/fail line, run against every commit before it counts as done. (§14, and .githooks/pre-push)

What to say when something fails live

Nothing about the hook floor is exercised live in front of a judge — it runs at commit and push time, before the demo starts. If a build-time gate genuinely blocks legitimate work during prep, the rule is: fix the gate and log why, never weaken it to get past it — say that plainly if asked, rather than pretending it never happened.
